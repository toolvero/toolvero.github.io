SSL/TLS Certificates Explained: CSR, X.509, Expiration and Troubleshooting

A practical overview of certificate requests, issued X.509 certificates, validity dates and the checks administrators perform during TLS troubleshooting.

What is an X.509 certificate?

An X.509 certificate binds identity information to a public key and is signed by an issuing certificate authority (CA). TLS servers present certificates so clients can validate the server identity and establish an encrypted connection.

CSR vs certificate

A certificate signing request (CSR) is created before the certificate is issued. It contains the public key and request information and is signed using the corresponding private key. The CA validates the request according to its process and returns an issued certificate.

Important: a CSR and a certificate can be shared during normal PKI workflows, but the private key should remain protected. Do not paste private keys into browser tools.

Validity dates

Certificates include a validity window commonly described as Not Before and Not After. A certificate outside that period can be rejected by clients. Monitoring expiration before the Not After date is therefore an operational requirement, not just a PKI detail.

Subject, issuer and SAN

  • Subject: identifies the certificate subject.
  • Issuer: identifies the CA that signed the certificate.
  • Subject Alternative Name (SAN): carries DNS names or other identities the certificate is valid for. Modern hostname validation relies on SAN.

The certificate chain

A server certificate is often validated through one or more intermediate CA certificates up to a trusted root CA. A server can have a perfectly valid leaf certificate and still fail client validation if required intermediate certificates are not presented correctly.

Practical troubleshooting checklist

  1. Confirm the requested hostname is covered by a SAN.
  2. Check the certificate validity period.
  3. Verify the issuer and certificate chain.
  4. Confirm the server is presenting the intended certificate.
  5. Check whether the client trusts the relevant CA chain.

Useful OpenSSL checks

openssl x509 -in certificate.pem -noout -subject -issuer -dates
openssl req -in request.csr -noout -text
